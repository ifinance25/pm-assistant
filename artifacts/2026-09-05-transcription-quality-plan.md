# Качество расшифровки PM Assistant: диагноз и починка

## Context

Расшифровки звонков плохого качества. Разбор кода и замеры самих аудиофайлов показали: **основная причина не в распознавании речи, а в записи звука**. Бот местами пишет полную тишину, а Whisper на тишине выдумывает текст и складывает выдумку в базу как настоящую расшифровку. Там, где звук всё-таки есть, он слишком тихий, и нормализации громкости в коде нет ни в одном месте.

Цель: расшифровка настоящего звонка на русском становится пригодной для работы без ручной правки, и каждая реплика подписана именем участника.

Ограничения от пользователя:
- Новых платных подписок не заводим. Используем то, что уже оплачено: локальный Whisper (бесплатно), подписка Claude Code (`CLAUDE_CODE_OAUTH_TOKEN`) для вычитки текста, аккаунт Supadata (`SUPADATA_API_KEY`).
- **Важно:** Claude не распознаёт речь. У модели нет входа для аудио. Она умеет только править уже готовый текст, что в проекте уже сделано в `revise.ts`. Заменить ею Whisper технически невозможно.
- Разделение по спикерам (кто что сказал) нужно. В плане оно делается на стороне записи звука (фаза 4), поэтому не зависит от выбранного движка.
- Supadata подключаем вторым движком на выбор (фаза 6), локальный Whisper остаётся значением по умолчанию.

### Фаза 2. Громкость и срез тишины

`src/adapters/stt/trim-silence.ts`, функция `trimEdgeSilence`:

1. **Всегда прогонять звук через ffmpeg.** Сейчас три ветки (`:134`, `:147`, `:154`) возвращают исходный файл нетронутым — нормализация до него не дойдёт. Переписать так, чтобы `speech.wav` создавался всегда, а срез краёв был опциональной частью.
2. В команду вырезки добавить фильтры:
   ```
   -af "highpass=f=80,loudnorm=I=-16:TP=-1.5:LRA=11" -ac 1 -ar 16000
   ```
   `highpass=f=80` убирает гул. `loudnorm` выравнивает громкость до вещательного стандарта — это главный выигрыш для файлов на −38 dB.
3. Порог `SILENCE_NOISE` поднять с `-40dB` до `-50dB`: на записи со средней громкостью −38 dB порог −40 dB съедает настоящую речь.

**Выкатить на прод** (сейчас код только локальный, `PM_Assistant.md:112`): `artifacts/deploy/sync.sh` + рестарт `pm-assistant-worker`.

**Проверка:** перерасшифровать `db62a0b2` и `60b10313` из regression-папки до и после. Прогнать WER-скрипт из фазы 5.

### Фаза 3. Починить захват звука

`app/bot/zoom-web/capture-audio.js` — три правки.

**3.1. Основной путь — захват звука вкладки.** Флаг `--auto-select-tab-capture-source-by-title=PM Assistant Zoom` уже стоит в `join.mjs:419-431`, но `getDisplayMedia` нигде не вызывается. Добавить:
```js
const tab = await navigator.mediaDevices.getDisplayMedia({
  video: true, audio: true, preferCurrentTab: true,
});
```
Флаг автовыбора убирает диалог выбора окна. Захват вкладки берёт звук на выходе браузера — он работает независимо от того, как именно Zoom Web SDK отдаёт аудио. Существующий хук `RTCPeerConnection` оставить как запасной путь.

**3.2. Замер громкости в реальном времени.** На `mixer.dest` повесить `AnalyserNode`, каждые 2 секунды считать RMS (среднюю мощность сигнала) и слать в лог через `pmPushAudio`. Если 20 секунд подряд ноль — переключиться на запасной хук и записать в лог причину. Это и есть ответ на открытый вопрос «почему тишина».

**3.3. Не терять хвост записи.** `stopPageCapture` (`join.mjs:373-386`) ждёт фиксированные 1200 мс — из-за этого webm обрывается. Заменить на: `recorder.requestData()` → `recorder.stop()` → дождаться события `stop` **и** подтверждения, что последний `dataavailable` дошёл до `pmPushAudio`.

**Проверка:** живой звонок Zoom. `ffmpeg -af volumedetect` на полученном файле должен показать `mean_volume` выше −35 dB. Это блокирующий критерий: без него фазы 4-5 бессмысленны.

### Фаза 4. Разделение по спикерам

**Важный риск, который надо проверить первым:** Zoom Web SDK во многих режимах отдаёт **один смешанный аудиопоток**, а не отдельную дорожку на участника. Если так — записать каждого отдельно нельзя в принципе. Первый шаг фазы: залогировать `pc.getReceivers()` на живом звонке и посчитать аудиодорожки.

Поэтому основной механизм не зависит от числа дорожек — **таймлайн активного спикера**:

1. В `capture-audio.js` подписаться на сигнал активного спикера Zoom Web SDK (`client.on("active-speaker", ...)`). Запасной вариант — опрос DOM: у говорящего участника Zoom подсвечивает плитку.
2. Копить массив `[{ atMs, name }]` и в конце звонка выгружать в `<meetingId>.speakers.json` рядом с аудио (`join.mjs`, тот же `createAudioWriter`-механизм).
3. Новый `app/src/adapters/stt/diarize.ts`: функция `assignSpeakers(segments, timeline)` — каждому сегменту Whisper ставит имя того, кто говорил дольше всех внутри окна `startedAtMs..endedAtMs`. Если таймлайна нет — оставить `Спикер 1` как сейчас.
4. Подключить в `liveTranscribe` (`live.ts:35-41`) вместо захардкоженного `speaker: "Спикер 1"`.

Бонус, если отдельные дорожки всё-таки придут: писать каждую своим `MediaRecorder`, расшифровывать по отдельности, склеивать по таймкодам. Тогда разделение точное. Ставить это условной веткой, не основным путём.

Схема БД менять не надо: `transcript_segments.speaker` уже есть (`src/db/schema.ts:117-124`).

**Проверка:** тест `diarize.test.ts` на синтетическом таймлайне. Затем живой звонок вдвоём: имена в расшифровке совпадают с реальными репликами.

### Фаза 6. Supadata как второй движок на выбор

Аккаунт уже оплачен. Ключ `SUPADATA_API_KEY` лежит в `/Users/ifinance/.claude/settings.json` в блоке `env`; на прод его кладёт пользователь в `/etc/pm-assistant.env`. Навык-справочник: `/Users/ifinance/.claude/skills/supadata-transcript/SKILL.md`.

Что даёт: распознавание уровня большой модели без нагрузки на 2 ГБ памяти EC2. Для файлов Supadata включает режим `generate`, то есть настоящее распознавание речи, а не выкачивание готовых субтитров.

**Блокер, который надо решить до внедрения: файл должен быть доступен по публичной ссылке.** Приложение по проекту слушает только `127.0.0.1`, записи лежат в `/opt/pm-assistant/app/data/audio/`. Варианты:
- временная подписанная ссылка на публичном порту EC2 (`16.171.52.89`), живёт 15 минут, одноразовый токен в пути;
- заливка файла в объектное хранилище с временной ссылкой.

Оба варианта означают, что запись звонка на короткое время выходит наружу. Это изменение приватности продукта, решение за пользователем. Пока оно не принято — фазу не начинать.

Реализация (после снятия блокера):
1. `app/src/adapters/stt/supadata.ts` — `GET https://api.supadata.ai/v1/transcript?url=<ссылка>&text=false&lang=ru`, заголовок `x-api-key`. На больших файлах приходит ответ 202 с `jobId`: опрашивать `GET /v1/transcript/<jobId>` с паузой, пока не готово.
2. Маппинг ответа в существующий тип `SttSegment` (`src/adapters/stt/index.ts:7-12`): `offset` → `startedAtMs`, `offset + duration` → `endedAtMs`, `text` → `text`. Поля спикера в ответе Supadata нет — его проставит `assignSpeakers` из фазы 4.
3. Расширить `SttEngine` (`index.ts:23-26`): `kind: "whisper-cli" | "supadata"`. Выбор движка — переменная `PM_ASSISTANT_STT_ENGINE`, по умолчанию `whisper`. `createSttAdapter` уже устроен как фабрика, ломать её не надо.
4. Проверки тишины и блок-лист выдумок из фазы 1 применять **до** отправки — незачем платить за расшифровку тишины и выкладывать её наружу.
5. Откат: при ошибке или таймауте Supadata — вернуться на локальный Whisper, не ронять встречу. Тот же принцип, что уже применён для LLM при 429 (`pipeline.ts:107-114`).

Неизвестное, которое закроет только прогон: качество Supadata на русском, лимиты по размеру и длительности, расход кредитов. Мерить тем же WER-скриптом из 5.1 на тех же трёх файлах — это и есть способ выбрать движок по умолчанию.

**Проверка:** `node artifacts/deploy/wer.mjs --engine=supadata` против `--engine=whisper` на одних и тех же трёх записях. Побеждает меньший WER.
